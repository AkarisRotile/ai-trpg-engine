# AI 全自动跑团引擎 · 总设计案

> 项目代号：**COC-Table**
> 一句话定位：KP 与 PL **全部由 AI 担任**的《克苏鲁的呼唤》第七版跑团引擎。
> 每个座位独立 API Key，可视化前端由 exe 启动，跑团过程全自动。

---

## 一、这个项目真正的技术难点

不是"调 API"，也不是"画界面"。真正的难点只有一个：

> **让模型处于"我正在跑团"，而不是"我正在扮演一个跑团的玩家"。**

这两句话在人类读来差不多，在模型那里是**两条完全不同的解码路径**。前者是**续写**（continue），后者是**表演**（perform）。一旦落入后者，你会稳定地看到这些症状：

- 输出"好的，作为艾德温，我会先观察四周。"——开场白 + 元层自述。
- 写小说体第三人称旁白："卡特小心翼翼地推开门，发现门后空无一物。"——**替 KP 做了判定**。
- 输出"我希望 KP 能给我一个聆听检定。"——把 KP 当成对话对象而不是世界。
- 每轮复述一遍局势、总结一遍已知信息——因为它以为自己在"汇报"。
- 三个 PL 互相看见对方的 `think` 后开始互相迎合，人设塌陷成同一个声音。

这五条几乎全部源自同一个病根，下面拆开讲。

### 根因 1：聊天模型的后验是"用户下任务 → 助手完成"

当 system 里写"你是一名 PL / 你要扮演一个玩家"时，**"PL"被解析成一个任务角色，而不是一个身份**。模型的自我模型（assistant）没有被替换，只是被套了一层戏服。所以它输出的是"关于这个角色的规划"，而不是"这个角色的行动"。

**模型对"你是 X，此刻你在 Y"的处理方式是续写，对"你扮演 X"的处理方式是表演。**

### 根因 2：对话格式本身在提示元层

只要 KP 的话是"请各位玩家描述你们的行动"，这就是一句**对助手的指令**。指令–响应格式一出现，助手人格立刻回位。这是"跑团"与"扮演跑团"的分水岭：

- **跑团** = 世界对角色施加压力。
- **扮演跑团** = 人对 AI 下达任务。

### 根因 3：元语言污染

只要 prompt 里高密度出现"跑团 / 模组 / PL / KP / 规则 / 扮演"这些**元语言**，模型就会把当前上下文判定为"在讨论或演绎跑团这件事"，于是它开始**表演跑团**——写旁白、替别人写台词、跳过判定直接宣布成功。

### 根因 4：没有身体、没有当下

抽象身份产出抽象输出。模型需要"现在、这里、手上有什么、刚才三秒发生了什么"这类**感知锚点**，才会进入行动模式。

## 二、五条结构性对策（这是本项目的地基）

> 总原则：**用结构逼出行为，不用祈使句求行为。**
> 特别地，**不要**在 prompt 里写"不要扮演，要沉浸"——否定式指令会激活被否定的概念（"不要想大象"）。禁令要少，格式要有。

### 对策 1 · 把"扮演"这个词从整个系统里删掉

全项目禁用词表：`扮演`、`模拟`、`你是一名玩家`、`PL Agent`、`你需要输出`。
替换为**身份断言 + 现在时 + 空间锚点**：

```
你是艾德温·卡特，34 岁的民俗学者。
此刻你站在阿卡姆镇郊外那栋废弃洋馆的门厅里，雨水正从你大衣下摆滴到地板上。
```

### 对策 2 · 消息历史本身就是身份载体（最强的一条）

**不要**每回合拼一个巨大的、结构每次都变的大 prompt。为每个 PL 维护一个**真实的 messages 数组**：

| 角色 | 内容 |
|---|---|
| `system` | 身份断言 + 交战规则（简短、恒定、每轮不变） |
| `user` | 世界发生的事（KP 叙述原文，纯虚构，**不含任何祈使句**） |
| `assistant` | **该 PC 过去说过的原话与做过的动作，逐字保留** |

模型不是在"回答一个问题"，而是在"续写一段它自己已经写了很久的记录"。角色一致性由历史自身维持，不再靠每回合重新说服。

**配套机制 · 入戏锚定（Anchoring Pass）**：开局时先让每个 PL 用**正式输出通道**生成一段"开场前 30 秒，你的角色在做什么"的短内容，这段内容会作为该 PL 的第一条 `assistant` 历史。它同时干三件事：定妆、给历史做 few-shot、把模型自己的合规输出变成后续的格式参照。

> 有了对策 2，漂移率能压掉一大半。这是投入产出比最高的一环。

### 对策 3 · KP 绝不直接跟 AI 说话，世界只是"发生"

引擎给 PL 的回合信号必须是**结构性记号**，而不是请求：

- ❌ `请描述你的行动。`
- ✅ 记录末尾追加 `⟨等待你的行动⟩`

世界消息与指令消息的语域必须彻底分开。同时**身份声明放在 messages 数组最前且恒定不变**，让历史自己承担"我是谁"。

### 对策 4 · 把"掷骰/规则"和"虚构"分到两个语域通道

元层泄漏最爱从规则沟通里渗出来。所以 PL 的每一次输出被切成四个**语域互不污染**的通道：

| 通道 | 语域 | 可见性 | 作用 |
|---|---|---|---|
| `<think>` | 角色第一人称内心 | 仅自己 | 保留角色的推理能力，但用角色的口吻 |
| `<act>` | 第一人称、现在时、**只写尝试不写结果** | 全体 | 真正的行动与对白 |
| `<ooc>` | **电报体机械协议**，如 `检定申请 聆听` | 仅 KP + 引擎 | 掷骰申请。禁止客套——一客套就回助手人格 |
| `<mem>` | 结构化记忆增量，机器消费 | 仅引擎 | 记忆回写，不进他人上下文 |

**四个通道让"我"始终是角色，规则只是角色伸手去够的一个开关。**

### 对策 5 · 引擎独占全部事实

骰子由 Python 掷，HP/SAN/技能值由引擎持有，模型只能**申请**和**叙述**。

这条不只是防作弊。它同时消灭了模型的"作者人格"——当模型发现自己**无法**决定结果时，它就只剩"行动"这一条路可走。

### 兜底 · 元层哨兵（Meta Linter）

生成后正则扫描元层标记（`作为PL` / `作为一个玩家` / `请问KP` / `我希望` / `我是AI` / `As an AI` / `让我来` / `好的，` / `接下来我`）。
命中 → 带命中片段做**一次静默重写**；再命中 → 裁掉该行并在 UI 标记。

有了对策 1–5，这一层通常只在极端情况下触发，但它是必要的保险。

## 三、系统架构

```
┌─────────────────────────────────────────────────────────────────┐
│  UI 层（pywebview 原生窗口，渲染 HTML/CSS/JS）                    │
│  设置 · 席位管理 · 跑团主日志 · 角色卡 · 记忆树 · 骰子台 · 存档    │
└────────────────────────────┬────────────────────────────────────┘
                             │ window.pywebview.api.* (JS ⇄ Python)
┌────────────────────────────▼────────────────────────────────────┐
│  应用门面 engine/app.py  —— 唯一对 UI 暴露的接口，全部 pure Python │
├─────────────────────────────────────────────────────────────────┤
│  LLM Router     │ Rules Kernel  │ Memory Store  │ Module Library │
│  每座位独立      │ COC7 骰子/判定 │ 三层记忆      │ 模组扫描/场景  │
│  client + key   │ HP/SAN/技能   │ 检索式注入    │ handout 保密   │
├─────────────────────────────────────────────────────────────────┤
│  Prompt Compiler      │ Turn Manager     │ Meta Linter          │
│  四通道输出契约        │ 探索轮/战斗轮     │ 元层漂移哨兵          │
├─────────────────────────────────────────────────────────────────┤
│  Agent Runtime (KP Agent / PL Agent)  —— 座位即身份               │
└────────────────────────────┬────────────────────────────────────┘
                             │ OpenAI 兼容 HTTP (requests)
              ┌──────────────┴──────────────┐
              │  DeepSeek 官方  ·  自定义 URL │  ·  离线 Mock
              └─────────────────────────────┘
```

**分层铁律**：`engine/` 不 import 任何 UI 库；UI 不直接读文件。这样引擎可以独立跑自动化测试、未来换 Electron/Tauri 前端也不用改引擎。

## 五、核心数据模型

### 5.1 Seat（座位）—— KP 与 PL 是同一抽象

```yaml
seat_id: pl_1                # kp / pl_1 / pl_2 …
kind: PL                     # KP | PL
display_name: 艾德温·卡特
provider: deepseek           # deepseek | custom | mock
base_url: https://api.deepseek.com/v1
api_key: sk-****
model: deepseek-chat
temperature: 0.85
max_tokens: 1400
profile:                     # 仅 PL
  playstyle: 慎重解密流
  personality_traits: [对未知事物极度警惕, 重视队友协作]
character:                   # 仅 PL
  name: 艾德温·卡特
  occupation: 民俗学者
  age: 34
  attributes: { STR: 45, DEX: 60, INT: 80, CON: 50, POW: 75, SAN: 75, HP: 10, LUCK: 65, MP: 15, DB: "0", MOV: 8 }
  skills: [{ name: 图书馆利用, value: 75 }, …]
  inventory: [黄铜怀表, 速记笔记本与碳素笔, 小型手电筒]
```

**一个 PL = 一个 API Key = 一份独立记忆。** KP 也一样是座位，也可以配不同的模型（例如 KP 用 `deepseek-reasoner` 做裁定，PL 用 `deepseek-chat` 保持反应速度）。

### 5.2 Memory（三层记忆）

| 层 | 名称 | 变化频率 | 注入策略 |
|---|---|---|---|
| **L0** | `character_sheet` 角色卡 | 几乎不变 | **全量**注入 |
| **L1** | `situation` 情境 | 每场景 | **全量**注入 |
| **L2** | `chronicle` 编年史 | 追加式 | **检索式**注入 top-K |

L2 检索打分 = 场景标签匹配 × 2 + 关键词重叠 + 时间衰减。默认 K=12。

**关键设计**：磁盘上是结构化 YAML（人类可读可改、UI 可直接渲染），但**注入 prompt 时会被渲染成"角色的回忆"**，而不是让模型去"读自己的笔记"：

```yaml
# 磁盘上（YAML，规范存储）
chronicle:
  - { turn: 3, scene: scene_01, kind: clue, text: "大门是从外部被铁链反锁的。", tags: [门厅, 出口] }
```

```
# 注入 prompt 时（渲染为第一人称回忆）
你记得的事：
- 大门是从外面用铁链反锁的，短期内出不去。
- 壁炉里有半截没烧尽的羊皮纸，上面有符咒印记。
```

这一层转换很重要：直接丢 YAML 会让模型进入"我在读一份档案"的元姿态。

### 5.3 Module（模组）与信息隔离

```
模组 → KP 可见（全部）        ：secret_truth + 全部 scenes + handouts 索引
模组 → PL 可见（仅经 KP 分发）：当前场景叙述 + 已到手的 handout 原文
```

**硬隔离**：`secret_truth.md` 只在 KP 的 Prompt Compiler 里被读取，PL 的代码路径根本无法访问（不是"提示它别说"，是**取不到**）。Handout 只有引擎执行 KP 的 `grant_handout` 指令后，才追加进指定 PL 的记忆 L2，并在下次编译时出现。

## 六、回合循环（时序）

```
        ┌──────────────── KP Agent ────────────────┐
        │ 生成 <narr> 公开叙述                      │
        │      <secret> 幕后状态（仅自己）           │
        │      <state> 机器指令                     │
        └──────────────────┬───────────────────────┘
                           ▼
              [引擎执行 state 指令]
              掷骰 / 伤害 / SAN / whisper / grant_handout / advance_scene
                           ▼
        ┌──────────── 并行 PL Agents ──────────────┐
        │ 每个 PL 编译上下文：                       │
        │   system(身份) + history(自己+世界)        │
        │   + L0/L1 + L2 top-K + ⟨等待你的行动⟩      │
        │ → 生成 <think><act><ooc><mem>             │
        │ → 元层哨兵 → 引擎回写 L2                   │
        └──────────────────┬───────────────────────┘
                           ▼
              [引擎汇总：全体 act + 骰子结果 + OOC]
                           ▼
                     回到 KP Agent（下一轮）
```

- **探索轮**：所有 PL **同时**行动，互不可见当轮他人输出（避免互相迎合导致人设塌陷）。
- **战斗轮**：按 DEX 顺序依次行动，后者可见前者已发生的部分。
- **私密线索**：KP 用 `whisper` / `grant_handout` 私发给单个 PL，只有该 PL 的 history 会收到。

## 七、提示词工程（全文见 `engine/prompts.py`）

### 7.1 PL 输出契约（正向表述优先，禁令最少化）

```
<think>  {PC姓名}此刻心里的念头。第一人称，用你自己的口吻，不是分析报告。 </think>
<act>    你做了什么、说了什么。第一人称、现在时、只写你尝试的动作与说出口的话。 </act>
<ooc>    只在需要动用能力或装备时写。电报体，例如：检定申请 聆听。不需要就留空。 </ooc>
<mem>    需要记住的新事实，一行一条。没有就留空。 </mem>
```

关键点：`<act>` 里**只写尝试不写结果**。门后有什么、听没听清、这一枪中没中，都不是 PL 说了算。这条同时消灭了"作者人格"。

### 7.2 关键手法小结

| 手法 | 作用 |
|---|---|
| 身份断言（"你是 X，此刻你在 Y"）而非"你扮演 X" | 把解码路径从 perform 切到 continue |
| 真实 messages 历史 + assistant 逐字保留 | 历史自身维持人设，不靠每轮说服 |
| 入戏锚定 pass | 用自己的合规输出当 few-shot |
| 四语域通道分离 | 规则沟通不再污染虚构语域 |
| 世界消息零祈使句 + 结构记号 `⟨等待你的行动⟩` | 消灭"指令–响应"格式 |
| 引擎独占骰子与数值 | 消灭作者人格 + 防作弊 |
| 元层哨兵 | 兜底 |
| 禁用词表 | 从系统层面清除元语言污染源 |

## 八、首版（First Playable）范围与验收

**必须真实可用：**
1. exe 双击启动，弹出原生窗口，全套配置在界面里完成。
2. 座位管理：1 名 KP + N 名 PL（N 可自定义，含 N=1 单人跑团），每个座位独立 Key。
3. 双接口：DeepSeek 官方预设一键填 Key；自定义 base_url / key / model。
4. 离线 Mock 座位，零额度跑通全流程（用于验证与试用）。
5. 三层记忆：每座位独立 YAML 落盘，UI 可查看，检索式注入。
6. 模组库：丢文件夹即被识别；幕后真相与 handout 硬隔离。
7. COC7 骰子内核：d100 成功等级、奖惩骰、对抗、伤害、SAN。
8. 元层哨兵生效。
9. 会话存档 / 续跑 / 导出跑团记录为 Markdown。
10. 导演指令：人类可随时向 KP 注入一句场外提示。

**验收证据**：Mock 模式跑满 ≥5 轮无异常 + 真实 API 模式跑通 ≥3 轮 + 双击 exe 截图/日志。

**长期路线（本轮不做）**：战斗先攻可视化网格、语音、地图、多 KP 联席、RAG 向量检索、模组编辑器。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 模型仍偶发元层 | 哨兵重写 + 入戏锚定 + 禁用词表，三层兜底 |
| PL 之间人设趋同 | 探索轮互不可见 + 生成时强制差异化 `playstyle` |
| 上下文爆炸 | L2 检索式注入 + 超过 N 轮把旧历史压缩成编年史摘要 |
| API 费用失控 | 每座位独立 max_tokens、回合上限、界面实时 token/费用统计 |
| 打包后路径错乱 | onedir + 所有数据目录相对 exe 定位，不写系统盘 |
